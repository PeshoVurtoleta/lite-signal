# WHY 1.11.0 -- `onSettled`, rebuilt as a creation-time capability

This is the redemption arc, and the keystone of the whole rebuilt line. `onSettled`
is the feature whose first implementation started everything: an always-checked drain
hook that cost ~7ns per flush through V8's inline/code-size budget and produced a
**+27-31% batched-update regression** (ledger #17). The line was reset to 1.8.0 and the
governing rule was written: nothing lands in a hot function body in the default build.

1.11.0 brings the feature back with its cost model **inverted** -- and in doing so
proves the rule can reclaim something that once looked incompatible with it.

## What ships

`createRegistry({ settled: true })` turns on the capability. `onSettled(fn)` registers a
drain-complete callback and returns an unsubscribe. On a registry built *without* the
option, `onSettled` throws and points at it. The callback fires **once per top-level,
non-empty, clean drain**: not per effect, not on a re-entrant flush during a drain, not
on an empty `flush()`, and not on a flush that threw -- so "settled" always means the
graph actually quiesced. It coalesces exactly where you would want: a `batch()` of many
writes, or a single write that fans out to many effects, is one settle.

## The inversion

The rejected hook asked, on every flush, "is anyone listening?" -- a check that lived
forever in the hot drain. This version asks the question **once, at `createRegistry`**,
and never again:

```
const flushEffects = CAP_SETTLED ? flushEffectsSettled : flushEffectsPlain;
```

`flushEffectsPlain` is the 1.10.0 drain, verbatim. A default registry binds it, so the
hot write path calls a byte-identical closure and pays literally nothing -- the cost is
zero *by construction*, decided before the first closure is built, not avoided by a
runtime branch. Only a registry built with `{ settled: true }` binds
`flushEffectsSettled`, which runs the same plain drain and then, if this was a top-level
call that actually did work, fires the callbacks. The profiler creates its registries
with the capability; production overlays never opt in and never pay.

This is the exact discipline the 1.7.0 `flushStrategy` closures established: select a
variant at build time via an immutable const, never dispatch through a mutable slot,
never check in the hot body.

## Why it is safe (proven, not claimed)

- `flushEffects` (plain body), `markDownstream`, `executeEffect`, `pullComputed` are
  **byte-identical** to 1.10.0 by sha256 over the extracted bodies. The only default-
  build change is that the `flushEffects` binding became a selected const -- the same
  form the flush strategy already uses.
- `1to1batch` on a default registry is neutral (the write path is unchanged);
  `createSignals` / `createEffects` are within noise (the capability is read once at
  `createRegistry`, never at creation).
- `test/31-onsettled.test.mjs` pins the semantics: throws without the capability,
  fires once per drain, coalesces under batch and multi-effect flushes, stays silent on
  empty / re-entrant / thrown flushes, and unsubscribes cleanly.

## What it unblocks

A precise "the batch has been delivered and the graph is quiet" signal is what a
scheduler, a test harness, or a frame coordinator needs to know a reactive update has
fully landed. It is also the notification the trace twin (1.12.0) will hang its
per-flush records off. `onSettled` proves the twin's model before the twin exists: a
capability selected at build time, invisible and free unless asked for.
