PREALLOC / PROTOCOL NOTE (read this first). These numbers are the default-config run
(prealloc: "eager" -- pools constructed up front, the zero-allocation-in-hot-path
contract). They come from the one-engine-per-cold-process protocol (run-all-bench.sh:
FW=<engine> per child, medianed by aggregate.mjs): each engine has its own
ReactiveNode/signal shape, so sharing call sites across engines in one process would
degrade their inline caches monomorphic -> megamorphic and let nursery-allocating
engines borrow a prior engine's warm heap. The isolated protocol below is the correct
comparison.

WHAT MOVED 1.5 -> 1.6. The 1.2.2 -> 1.3.0 -> 1.4.0 -> 1.5.0 engine had byte-identical
hot paths across those minors. **1.6.0-alpha changes that**: two new mutation-hook
opcodes -- op 6 (flush-pass-start) fired once per `flushEffects` pass and op 7
(effect-enqueue) fired inside `markDownstream`'s inner loop when a dirty subscriber is
enqueued -- add one branch-predicted `null` check to the hot path
(`if (mutationHook !== null) mutationHook(...)`). Gated -> zero cost when no profiler
is attached; branch present regardless. The `flushPasses` counter on `stats()` (the
12th key) advances only while a hook is attached. sha256 over the extracted function
bodies of `pullComputed`, `executeEffect`, `allocateLink`, `severTail`, `createNode`,
`runCleanup`, `disposeNode`, `createRoot`, `createScope` matches the 1.5.1-beta.1
engine byte-for-byte; `markDownstream` and `flushEffects` legitimately changed for
the new opcodes and are pinned by hash on this cycle instead.

The measurable footprint of that extra gate is small but real: KAIROS moves from
-7% -> -12% and DEEP CHAIN from -14% -> -21% between the 1.5.0-beta and 1.6.0-alpha
sweeps here. Two hot loops iterate ~1000-25000 times per rep, so a single extra
predicted branch per iter is enough to explain a few-percent swing on the cheap
propagation shapes. The wide-aggregation shapes (MUX +35%, DYNAMIC DAG +43%,
SELECTIVE DAG +49%, SMALL SELECTIVE +29%) still cluster at their prior magnitudes
because the ratio of pool retracking to marker walks favors lite by orders of
magnitude there.

(prealloc: "lazy" trades a little first-construction allocation on the dynamic shapes
for a smaller resident heap and faster cold start; steady state is identical.)

deltaheap = transient heap allocated during the timed loop (GC pressure). Reported
            below as the AVERAGE delta-heap across reps -- on this 10-year-old host a
            single rep's GC timing can inflate the average, so the near-zero shapes
            read as small non-zero averages; their median floor is the ~0.3KB
            pool-reuse value (true zero-GC steady state).
retained  = heap surviving a forced GC after the loop (leaks / live graph).
            Structurally unchanged from prior minors (same graph, same pool); not
            separately re-measured this cycle.
sink      = anti-DCE Float64Array validated non-zero after the loop.

WHY THE WINS CLUSTER WHERE THEY DO:
  The shapes where lite wins BIG are the allocation-heavy ones -- the dynamic DAGs
  (read order flips every iteration, dense fan-in) where alien churns the nursery.
  Run in isolation, alien pays the full GC cost of that churn and lite's
  zero-allocation pool pulls 29-49% ahead. The cheap propagation shapes (KAIROS,
  BROADCAST, DEEP CHAIN) barely allocate, so there is no GC tailwind for the pool to
  exploit; on those, the mutation-hook gate is a visible fraction of per-iteration
  cost, and the cheaper the underlying propagation the larger the fraction. The
  wide-aggregation wins are unchanged because those shapes spend so much time on
  retracking that adding one branch per subscriber walk is round-off.

  The honest summary: lite-signal's advantage is precisely where its zero-GC design
  pays off -- high-churn dynamic graphs and wide fan-in (MUX +35%). On the cheap
  low-allocation stable shapes it runs at parity with alien (-3% to -12%). The
  losses are BROADCAST (-10%, pure fan-out), KAIROS (-12%, gate-cost visible), and
  the 256-deep pipeline (DEEP CHAIN -21%), where alien's flatter representation
  wins on long propagation paths -- the added gate-cost per level compounds. When a
  1.6 profiler is attached (mutationHook not null) these gate branches would take
  the taken path anyway and the observable would be the profiler's own cost, not
  the gate itself.

Architectural reading:
  - lite-signal leads on fan-in (MUX) and the dynamic/selective DAGs -- the high-
    churn and aggregation patterns that dominate dashboards, scoreboards, and HUDs
    under live input -- and remains the only zero-deltaheap library on every truly
    stable scenario.
  - alien-signals edges BROADCAST, KAIROS, and the 256-deep pipeline (DEEP CHAIN),
    and runs at parity on LARGE WEB APP and WIDE DENSE. The retracking machinery
    (version-stamped O(1) reconciliation + markEpoch clean-read short-circuit,
    shipped 1.1.4) is what keeps lite ahead on the dynamic DAGs while shipping zero
    allocation.
  - 1.5.0 -> 1.6.0-alpha adds two hook-gated fires (op 6 in flushEffects, op 7 in
    markDownstream) plus `flushPasses` on stats(). The gate is one branch-predicted
    `null` check per fire site; measurable on KAIROS/DEEP CHAIN (a few percent
    swing on the cheapest shapes where every branch matters), invisible on the
    allocation-dominated shapes. `getOwner` / `runWithOwner` from 1.5.0-beta.2 land
    on this line and touch no hot path (verified: `runCleanup` / `disposeNode` /
    `pullComputed` bodies byte-identical to 1.5.1-beta.1). `createScope` (the new
    1.6.0 lifecycle primitive) composes existing primitives -- also no hot-path
    effect.

Profiling harnesses new in 1.6 (`harness/burst-dag.mjs` and `harness/pull-stress.mjs`):
  Both consume the new op 6/7 counters. burst-dag characterises the js-reactivity-
  benchmark burst shape (256->512x32, fanIn 8, burst 16) and reports flush passes
  per burst + max recomputes per node -- if both are 1, there is no coalescable
  redundant work and the gap on that shape is pure locality. pull-stress binary-
  searches the exact pull-mode recursion overflow depth on the current engine
  (~5000 chained computeds, per the roadmap), reports per-level cold-pull cost, and
  reports steady-state cached-read cost as an O(1) sanity check (should be
  independent of depth via the 1.1.4 markEpoch short-circuit). Run with
  `npm run profile:burst` / `npm run profile:pull`.

VersionMatrix gate (harness/VersionMatrix/): this bench is the public evidence
  surface; the same-host regression gate is in harness/VersionMatrix. It captures
  floor, rolling, and candidate in one cold-process run and blocks a publish that
  regresses frame.avg by >5% (rolling) or >10% (floor) on the four workloads that
  map to the rows above (reactive-graph-mix, deep-chain, broadcast-fanout,
  dynamic-dep-churn). 1.5.0-beta introduced an identical-code guard: when a
  candidate's Signal.js sha256 matches a baseline's, that axis is marked SKIP
  structurally instead of being flagged by noisy median variance. **On 1.6.0-alpha
  the gate is expected to RUN (not skip) vs the 1.5.1-beta.1 rolling baseline**
  because `markDownstream` / `flushEffects` legitimately changed and the sha256 no
  longer matches. Runs on prepublish; details in harness/VersionMatrix/README.md.
