# WHY 1.10.0 -- named nodes + `whyDirty()`

The rebuilt line's rule is one-or-two features per cut, each bisectable to a
single cause, each landing only after it proves it did not touch the hot path.
1.10.0 is the first cut aimed squarely at the profiler direction: it makes the
default build able to *explain itself*, by name and by cause, with zero cost
when you do not ask.

## What ships

**Named nodes.** `signal(v, {name})`, `computed(fn, {name})`, `effect(fn, {name})`.
A name lives in a registry-side `Map<id, name>`, populated only when you pass
one. No field is added to the node; the handle shapes pinned by `21-perf-pins`
(signal 6 own props, computed 4) are unchanged. `describe()` / `describeNode()`
return `name` when present. Devtools and the profilers can now render `hp`
instead of `#412`.

**`whyDirty(handle)`.** The pull-side answer to "why will this recompute" /
"why did this fire". For a computed it walks its deps and reports each one whose
version moved past the observer's `evalVersion` -- the *exact* predicate
`pullComputed` uses:

```
((dep.version - evalVer) | 0) > 0
```

against the **observer's** `evalVersion`, and it traces transitively down to the
underlying **signal write** (`rootCause`). It is read-only: it never calls
`pullComputed`, so it cannot recompute anything or move the clock it is
describing. It allocates freely -- it is a diagnostic on your cold path, never
invoked by the engine.

## The predicate mattered

The obvious sketch -- report a dep when `src.version !== src.evalVersion` -- is
wrong twice over. A plain signal never evaluates, so its `evalVersion` stays 0;
`version !== 0` is true for *every signal that was ever written*, so the sketch
reports the whole dependency set as the reason. And `!==` ignores the 32-bit
modular epoch wrap the engine relies on. The correct test compares each dep's
version against the **computed's** `evalVersion` with modular distance -- the
same line `pullComputed` runs. The discriminator test pins this: write one of
two signal deps and `whyDirty` must return exactly `[a]`, never `[a, b]`.

## Why it is safe (proven, not claimed)

The whole feature is confined to creation paths and cold diagnostics. The four
hot propagation bodies -- `markDownstream`, `flushEffects`, `executeEffect`,
`pullComputed` -- are **byte-identical** to 1.9.0, proven by sha256 over the
extracted function bodies, not asserted:

```
markDownstream   c0d2db2b...  OK
flushEffects     b39a260f...  OK
executeEffect    732cc3c9...  OK
pullComputed     f2162f01...  OK
```

Because the write path is the frozen `set`/flush cycle, `1to1batch` is neutral.
The only creation-path change is a single guarded comparison
(`opts !== undefined && opts.name !== undefined`) that short-circuits on the
unnamed fast path, so `createSignals` / `createEffects` stay within noise. This
is the same discipline that made the earlier `onSettled` regression findable:
nothing lands in a hot body in the default build.

## What it unblocks

`lite-trace` / `lite-hud` / `lite-devtools` can label graphs by name and answer
"which write dirtied this?" directly from the engine, with no instrumentation
and no cost to production overlays. It is the read-only companion to the
build-time trace twin slated for 1.12.0: names + `whyDirty` describe *what and
why*; the twin will record *when and how long*.
